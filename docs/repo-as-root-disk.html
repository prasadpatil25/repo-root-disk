Design note, revised against measurements

Repo as Root Disk

Committing a browser Linux VM's overlay back into a git host, so machine state gains version control semantics at zero infrastructure cost.

Status Full loop proven end to end Date 29 Aug 2026 Evidence 7 storage runs plus 4 VM runs, public and private Target v86 fork
Problem

The loop is open in every existing system

Browser Linux stacks all treat remote storage as read only. CheerpX streams a pre-chunked ext2 image through HttpBytesDevice or GitHubDevice, writes land in IDBDevice, and OverlayDevice merges the two. The documentation is explicit that changes persist to IndexedDB rather than being written back to the source repository.

The consequence is that machine state is trapped in one browser profile on one machine. It cannot be moved, shared, reviewed, archived, or cited. Clearing site data destroys it.

This note specifies the missing edge: a sync agent that commits the overlay into the git host as ordinary git objects. Once that edge exists, the machine's history is a git history, and fork, diff, checkout, and bisect apply to a running environment.

Device layers

Two paths, asymmetric costs

The read path is confirmed viable. raw.githubusercontent.com answers cross-origin requests with Access-Control-Allow-Origin: *, honours Range with a genuine 206 Partial Content and a Content-Range header, and consumes no API rate limit at all. Ranged streaming of a base image from a repository works.

Reserve the API exclusively for writes and for fallback reads. This is still the single most valuable rule in the document, but it is now a preference rather than a necessity: API reads measured about 600 ms and draw on the 5,000 per hour primary budget, which a boot touching a few hundred chunks does not come close to exhausting. The CDN is an optimisation, not a dependency.

Fixed-size chunking is sufficient here. Content-defined chunking (the rolling hash used by casync and restic) exists to survive byte insertions that shift every subsequent offset in a file. A block device has fixed offsets and never shifts, so that benefit does not apply. Align chunks to the overlay's block size and take the simpler code.

Commit shape

One blob per chunk, or one blob per sync

Revised. The original recommendation preferred delta packs largely because they collapse N+3 requests into 4. Measurement shows requests are not the scarce resource, so that argument no longer stands. Chunk-exploded is now the default, since free cross-commit dedup and per-chunk addressability cost almost nothing.

Chunk size should now be chosen for transfer efficiency and write amplification, with no reference to request budgets. The measured curve is steep:

chunkp50 latencyms per MBeffective
64 KB791 ms12,6560.08 MB/s
256 KB1,328 ms5,3120.19 MB/s
1 MB1,822 ms1,8220.55 MB/s
4 MB2,569 ms6421.56 MB/s

Per-megabyte cost falls twentyfold from 64 KB to 4 MB, because every request pays a fixed round trip of roughly 400 ms before any payload moves. Against that, a large chunk amplifies small writes: at 4 MB a one-byte change costs 2,569 ms and 4 MB of upload, where at 64 KB the same change costs 791 ms and 64 KB.

So the hybrid survives, for a better reason than the one originally given. Use small chunks for scattered metadata writes where amplification dominates, and large packs for bulk transfer where the fixed round trip dominates. Compaction is where a run of packs gets folded into a chunk-exploded checkpoint.

Alignment amplification is now measured rather than argued. In the full loop, 550 KB of genuinely dirty data landed in 5 chunks of 256 KB, so 1.25 MB was uploaded for 550 KB of change, about 2.3 times. That is the real cost of chunk alignment on a small filesystem workload, and it falls with smaller chunks at the price of more requests. With requests shown to be cheap and bandwidth shown to be the binding term, the balance now favours chunks smaller than the 4 MB the transfer curve alone would suggest.

Sync protocol

Eight phases, three of which touch the network

  1. P1

    Quiesce

    Take the Web Locks lock for this machine ref, flush the guest, and seal the current dirty set into a closed epoch. New guest writes open the next epoch and never block. The flush is a correctness requirement, not hygiene: writing a file to a mounted filesystem produced zero disk writes, with all of them landing later at sync and umount. Snapshot without flushing and the user's most recent work is silently absent.

    0 requests
  2. P2

    Snapshot

    Read the sealed epoch's dirty block ranges out of IndexedDB. Everything from here on operates on an immutable snapshot, so a slow sync never stalls the VM.

    0 requests
  3. P3

    Chunk and hash

    Coalesce the captured ranges into a dirty-region set first, then split into fixed chunks aligned to the block size, then compute each chunk's git object id locally as sha1("blob " + len + "\0" + bytes). Verified against the server on 141 of 141 blobs with zero mismatches. Coalescing matters because capture granularity is the IDE transfer, not the sector: a format, mount, file write and unmount arrived as seven intercepted calls carrying 550 KB between them, roughly 79 KB per call against a 512 byte sector.

    0 requests
  4. P4

    Dedup probe

    Skip any chunk whose object id is already in the locally held manifest of pushed objects. Prefer the local manifest over asking the server: reads are cheap, but round trips are not.

    0 requests
  5. P5

    Upload, concurrently

    POST /git/blobs per new object, base64 encoded, at concurrency 4 to 8. Serial upload wastes the round trip: throughput scales almost linearly to 16-way with no latency penalty. Governed to roughly 150 writes per minute sustained, for reasons in the next section.

    N requests
  6. P6

    Commit

    POST /git/trees carrying the chunk entries and the updated manifest, then POST /git/commits with the previous head as parent. Roughly 450 to 800 ms each, measured.

    2 requests
  7. P7

    Publish

    PATCH /git/refs/heads/machine with force: false. Confirmed: a stale parent is rejected with 422 Update is not a fast forward, which gives a genuine compare and swap.

    1 request
  8. P8

    Prune

    Mark the epoch synced, add its object ids to the local manifest, keep the chunk cache. Nothing is deleted from IndexedDB until a later boot proves the commit is reachable.

    0 requests

Concurrency

One writer per machine ref, enforced at two levels. Within a device, the Web Locks API stops two tabs racing. Across devices, the compare and swap in P7 catches the race after the fact.

On a rejected ref update, fetch the winning commit's manifest and compare dirty sets. If the two epochs touch disjoint block ranges, rebase onto the new head and retry exactly once. If they overlap, stop and fork to refs/heads/machine-<timestamp>, then surface it to the user as a branch. Silently merging two divergent filesystem states corrupts the guest, so automatic merge of overlapping ranges is never correct.

Boot

Resolve the ref through the CDN, fetch the manifest blob, mount the base image with range requests, and hydrate the overlay index from the manifest. Overlay chunks are fetched lazily on first touch and cached in IndexedDB. Time to shell therefore depends on manifest size and hot block count, not on total image size.

Read-your-writes fallback. When the CDN returns 404 for a chunk the manifest says exists, fall back to GET /git/blobs/:sha for that chunk, always with Accept: application/vnd.github.raw, rather than failing the boot. This costs primary quota, which is plentiful, and it covers both CDN propagation lag after a fresh commit and any environment where the CDN is unreachable. A boot must never fail because an optimisation was unavailable.

Measured limits

The points limit is the only one that is enforced

Revised, and this was the largest error in the original note. It claimed the 500 per hour content-generating limit was the whole design constraint. Across five runs and roughly 1,400 writes, that limit never fired. Neither did the documented 80 per minute. The limit that does fire is the points system.

GitHub documents four limits that could plausibly bind. Only one does.

Two details matter for the implementation. The service applies backpressure before refusal: sustained eight-way ran at 628 ms p50 against 386 ms for the same concurrency in short bursts, so rising latency is an early warning worth acting on. And recovery is fast, retry-after: 60, which is itself proof this is a per-minute limit rather than an exhausted hourly budget.

The real cost model

Concurrency scales almost linearly, from 134 writes per minute at one-way to 2,021 at sixteen-way, with per-request latency flat at roughly 400 ms throughout. That removes request latency as a constraint and replaces it with bandwidth:

sync time = max( ceil(N / C) × 400 ms , bytes ÷ 1.5 MB/s )

Setting the two terms equal gives a crossover that depends on concurrency: chunk = bandwidth × roundtrip ÷ C, so about 600 KB serially, 75 KB at eight-way, 37 KB at sixteen-way. Below the crossover you are request bound and concurrency helps. Above it you are bandwidth bound and concurrency buys nothing, because it is the same uplink either way.

Concurrency does not raise the bandwidth ceiling, only reaches it. Sixteen 256 KB chunks at eight-way ran at 1.21 MB/s writing and 1.12 MB/s reading, against 1.56 MB/s for a single 4 MB blob with no concurrency at all. Eight-way turned a 20 second serial transfer into 3.3 seconds, a sixfold gain, and then stopped at the same ceiling a single large request already reaches. The model predicted 256 KB at eight-way would be bandwidth bound, and it was.

For the real workload none of this binds. A 76-chunk sync every five minutes averages 15 writes per minute, an order of magnitude under the 180 ceiling, and the burst itself completes in about two seconds at 16-way. The rate limit only appears in a benchmark. The forge is not rate-limited for this workload. It is storage-limited. That makes compaction the central problem of the design rather than a maintenance detail.

The consistent rule across all seven: an unsynced epoch is the only irreplaceable state in the system, so every failure path either preserves it or tells the user plainly that it is gone.

Compaction

The binding constraint, and the only operation that relieves it

Every blob pushed stays reachable through history, so an autosaving machine grows without bound. Neither commit shape avoids this; chunk-exploded merely slows it down through dedup. With rate limits shown not to bind for realistic workloads, this is the constraint that actually decides whether a machine can live in a repository indefinitely.

Re-baselining is the fix. Snapshot the whole disk into a parentless commit and move the ref to it, which makes every earlier object unreachable. This is the one place force belongs, because discarding history is the entire point of the operation.

What a re-baseline actually costs

Hashing every chunk of the 256 MB machine measured above:

measurevalue
chunks on disk1,024
chunks that are entirely zero990
distinct blobs for the whole disk7
naive snapshot256 MB
deduplicated snapshot1.75 MB
read and hash the entire disk9.8 s

Those figures only hold for a nearly empty disk. With 7.4 MB of real content written, the same snapshot grew to 39 blobs and 9.75 MB, and content deduplicated at 1.00x. Snapshot cost is approximately the size of the machine's actual content, so a populated 500 MB rootfs snapshots to roughly 540 MB.

That changes the scheduling answer materially. On a sparse machine a re-baseline costs about three or four incremental syncs and can run routinely. On a populated one, at roughly 512 KB per incremental sync against a snapshot of several hundred megabytes, compaction only pays for itself after something like a thousand edits. Compaction should be scheduled on the ratio of accumulated history to current content, not on a fixed interval and not on repository size alone.

What survives unchanged is the bound compaction delivers. After it the repository holds one commit and the distinct blobs of the current disk, regardless of how many syncs preceded it, so restore cost becomes independent of machine age. That property is what makes the operation worth having even when it is expensive.

The cost is reading, not writing. Uploading a snapshot is small because it deduplicates; reading the disk back to compute those hashes took 9.8 seconds at 256 MB and would take proportionally longer at 1 GB, since untouched chunks must be fetched from the streamed base. Compaction is a read-bound operation, which is the opposite of every other phase in this design.

Same caveat as the scale section. 990 of 1,024 chunks were zero because the disk is blank apart from a fresh filesystem. A populated rootfs would have far more distinct content, the snapshot would be much larger, and the crossover against incremental history would move. The shape of the argument survives; these particular numbers do not.

Private repos

The write path is identical, the read path is not

Measured against a private repository, the entire write half behaves exactly as it does on a public one: 149 writes per minute sustained with no refusal, a commit cycle at 10.7 seconds against 10.7 on public, compare and swap rejecting a stale parent with 422, and every locally computed object id matching the server. Nothing in the sync protocol needs to know whether the repository is private.

The read path does change, and for a specific reason. Authorization is not a CORS-safelisted header, so a browser must preflight before sending it, and raw.githubusercontent.com answers that preflight with 403 and no Access-Control-Allow-Headers. The request never leaves the browser. Without the header the same host returns 404, because the content is private. The old ?token= query parameter, which would have avoided the preflight entirely, no longer exists. jsDelivr serves public repositories only.

On a private repository there is no CDN read path from a browser. Every read goes through GET /git/blobs/:sha against the 5,000 per hour primary budget. Measured at 1.12 MB/s at eight-way concurrency, which is the same ceiling the CDN path would hit, since both share the uplink.

Always request chunks with Accept: application/vnd.github.raw. The default media type returns base64 inside JSON: a 65,536 byte blob comes back as 90,615 bytes on the wire, an inflation of 1.383. The raw media type returns exactly 65,536 bytes, matching the declared blob size. Measured head to head in one run at eight-way concurrency: 1.47 MB/s with the default media type against 1.72 MB/s raw, a 17 percent gain, with writes in the same run at 1.36 MB/s. The gain is smaller than the 38 percent payload reduction because per-request latency, roughly 1,000 ms for a 256 KB read, dominates transfer time at this chunk size. It is still one header for 17 percent, and it restores the expected asymmetry: with the raw type reads are faster than writes, where with the default type they were slower.

Three consequences follow. Ranged reads disappear, because the blobs API returns whole objects, so chunk size becomes the read granularity and a 4 KB guest read pulls an entire chunk. The base image cannot be a CDN-streamed release asset, so split it into blobs under 100 MB held in git and read them through the same path as everything else, which removes a special case rather than adding one. And GitHub Pages cannot publish from a private repository on a free plan, so host the application from a public repository and keep machine state in a private one, which is the right separation in any case.

Chunk size is squeezed from both sides here. Large chunks amplify reads, since a small random read pulls the whole chunk with no way to fetch a fragment. Small chunks multiply requests against the hourly primary budget: fully materialising 1 GB costs 256 requests at 4 MB, 1,024 at 1 MB, and 4,096 at 256 KB, the last being 82 percent of the hourly allowance. Somewhere around 512 KB to 1 MB balances the two, against 4 MB for a public repository where ranged reads make amplification a non-issue.

Portability

One operation, not five

Corrected. This section previously claimed that GitHub, GitLab and Forgejo all provide putBlob, putTree, putCommit and casRef with different spellings. They do not. The low-level git object write API is GitHub-specific.

hostgit object writescommit APIrequests per sync
GitHubblobs, trees, commits, refsnoneN + 3
Forgejoread onlyPOST /contents with files[]1
GitLabread onlyPOST /repository/commits with actions[]1

The portable abstraction is therefore a single operation, commit(files) → ref, which GitHub implements the long way round and the other two implement directly. Both Forgejo's files[] and GitLab's actions[] accept base64 content and produce one commit, so a sync that costs eleven requests on GitHub costs one on either of them. The host this design was built on has the most expensive API for this workload.

Two caveats sit behind that. The batch endpoints carry every chunk inline, so a sync that moves 1.8 MB of content becomes a single request body of roughly 2.4 MB once base64 encoded, and each host will have a limit that GitHub's spread-out approach never meets. And the compare-and-swap in P7 does not obviously port: GitHub's force: false gives fast-forward-only semantics on the ref, while Forgejo offers per-file sha checks and GitLab offers start_sha, neither of which is the same guarantee. Concurrency safety needs re-establishing per host rather than assumed.

All three answer cross-origin requests with Access-Control-Allow-Origin: *, so the browser side ports without change. Rate limiting does not: GitLab advertises its limits in response headers even unauthenticated, at 500 per minute for anonymous API traffic, which is a different shape entirely from GitHub's points system.

Two reasons this is not premature abstraction. First, GitHub's acceptable use policy states plainly that it is not a content delivery network or a general purpose file host, so a design that leans hard on the free tier is one policy enforcement away from breaking. Second, running the same protocol against a self-hosted instance converts a vendor specific trick into a property of git hosts, which is the difference between a blog post and a paper. The measured envelope above is one account on one network, and the points ceiling in particular deserves replication elsewhere.

Open

What is still unmeasured

CDN propagation window. The gap between committing through the API and the content becoming readable through raw.githubusercontent.com is unknown, because the test machine had a local block on cross-origin CDN requests. The read-your-writes fallback in P7 covers it either way, but the window's size decides how often that fallback fires.

Replication. Every number here comes from one account, one network, one afternoon. The points ceiling especially may vary with account age or reputation.

Gate

Where this stands

The storage half is measured. Blobs, trees, commits, and compare-and-swap ref updates all work from a plain page with no server, at known cost, with locally computed object ids matching the server on every one of 141 blobs. The read path is confirmed at the protocol level, with cross-origin ranged reads on public repositories and an API-only path on private ones.

The dirty set is reachable, and capture is lossless. This was the assumption every phase of the protocol rested on, and it is now tested rather than assumed. In a v86 guest with a blank 16 MB disk on the IDE primary master, wrapping buffer.set on the constructed device captured exactly one write for one dd of one sector, and zero writes during boot. Replaying that captured set onto a blank buffer reproduced the live disk with zero differing bytes across all 16 MB. Not merely the marker in the right place: the entire device reconstructed identically.

Two details make the result worth trusting. Boot captured nothing, so the wrapper is not counting unrelated traffic. And one guest write produced exactly one intercepted call, so the IDE path funnels through a single choke point with no amplification at the capture layer.

It also survives a real workload and a real reboot. Formatting the disk with mke2fs, mounting it, writing a file and unmounting produced seven intercepted calls across stages that repeatedly rewrite the same structures, since ext2 lays down a superblock, a backup at block 8193, and rewrites both on unmount. Replay in capture order still reproduced the disk with zero differing bytes, so last-writer-wins is correct rather than merely plausible.

Then the strong form: a second machine was booted from nothing but the replayed write set, mounted the filesystem, and read back the file the first machine had written. That rules out the remaining worry that capture might be quietly incomplete, because a filesystem missing metadata does not mount at all. Byte equality could in principle be luck; a successful mount cannot.

It holds on the production device stack too. Repeating the whole sequence with the disk streamed over HTTP, so that v86 constructs an async chunked buffer rather than an in-memory one, needed no separate hook: the same interception point captured the same seven calls. Verification there cannot compare buffers, since that buffer's get_buffer returns nothing, so it cross-checks against the device's own record instead. Of the 2,164 blocks the device itself flagged as written, zero failed to reproduce from the replayed set, and a second machine again booted from it and read the file back. The reference for that check comes from the device rather than from the interceptor, which makes it the stronger of the two.

One detail the tests share by construction and the implementation must not: replay here starts from zeros because the base image is blank. In the real system replay is base plus captured writes, never blank plus captured writes.

The full loop

The whole thing runs. A guest booted with its base disk streamed over HTTP, formatted it, wrote a file and unmounted. The captured set was coalesced, hashed locally, uploaded as git blobs, committed with a manifest, and published on a machine ref. A second machine was then rebuilt from that commit alone, resolving the ref, reading the manifest, fetching the chunks, reconstructing the disk, booting, and reading the file back.

stageresult
captured7 writes, 550 KB, zero during boot
coalesced5 dirty chunks of 256 KB, at indices 0 to 2 and 32 to 33
uploaded5 blobs, 1.25 MB
sync cost9 requests, 5.1 seconds
restoremanifest plus 5 chunks, rebuilt, booted, marker read back

Those chunk indices are ext2's own layout showing through: 0 to 2 covers the superblock, group descriptors, bitmaps and first inode table, and 32 to 33 covers the backup superblock at block 8193. The coalescing step is tracking real filesystem structure rather than smearing across the disk.

A sync costs nine requests and five seconds. Against a ceiling of 180 writes per minute, a machine could sync roughly every four seconds indefinitely before the rate limit noticed. The design is not close to any limit it was originally written to respect.

Incremental syncs

Six successive syncs of one machine, appending a line to a file between each:

syncdirty chunksuploadedcontent reusedtree referencesrequests
155069
2 to 622066

Tree references stay flat while uploads fall. Every commit after the first references all five chunks and uploads only the two that changed, so three chunks ride along for free. The consequence matters more than the saving: restore cost is constant in the number of syncs. Sync 6 references six objects, exactly as sync 1 did, so rebuilding after a hundred syncs would still fetch five chunks, where a delta-pack design would have a hundred packs to replay. This, rather than request economy, is the real argument for chunk-exploded commits.

Content-level dedup contributed nothing. The reused column was zero in all six syncs. Every dirty chunk had genuinely changed, because appending a line rewrites inode timestamps as well as the data block. The saving above is incremental sync, not deduplication, and reporting them as one number would overstate the result.

The cost is storage, and it is severe. Each 17 byte append produced 512 KB of new git objects, and six edits left roughly 3.75 MB of blobs behind for about 100 bytes of user content. That adds a third axis to chunk sizing: alongside transfer efficiency and write amplification there is now repo growth per edit, which pushes toward smaller chunks than either of the other two would choose alone.

Scale

The same sequence on a 256 MB streamed disk, sixteen times larger:

Sixteen times the disk costs 1.4 times the upload. Of the 65 dirty chunks, 31 are entirely zeros and the remainder collapse into repeated patterns, so they reduce to seven distinct blobs. A naive upload would move 16.3 MB; the actual figure is 1.8 MB. The cost of putting a freshly formatted machine into a repository tracks the volume of distinct content, not the size of the disk.

This corrects the previous section. Content dedup contributed nothing at 16 MB and contributes roughly ninefold at 256 MB. Its value scales with disk size, because a larger filesystem carries proportionally more empty and repeated metadata. The negative result above is real but local, and generalising it would have been wrong.

Two supporting figures. Hashing all 65 chunks took 0.1 seconds, about 2 ms each, so the client side of a sync is free at this scale. The manifest costs roughly 51 bytes per chunk, so a 1 GB disk would carry about a 200 KB manifest, still comfortably a single blob. Boot took 5.7 seconds and mke2fs 2.3 seconds, the latter only because fixed_chunk_size enables read caching on the streamed buffer; without it every unloaded block read becomes a network round trip.

The same disk with real content on it

Writing 7.4 MB of genuine file content onto that disk, by copying the CD-ROM image into the filesystem:

This retracts the two paragraphs above, and part of the compaction section. Real content deduplicates at 1.00x, which is to say not at all: every chunk of genuine file data hashed uniquely. The ninefold incremental dedup and the hundredfold snapshot dedup measured on the blank disk were artifacts of empty space, not properties of the design.

Snapshot cost tracks content, not disk size. Adding 7.4 MB of content grew the full snapshot by 8 MB, a ratio of 1.08. A populated 500 MB rootfs would therefore snapshot to roughly 540 MB rather than the 1.75 MB a blank disk of that size would suggest. Sparse machines are cheap to store because they are mostly nothing; full machines cost what they contain.

One finding runs the other way. Alignment amplification depends on the write pattern. Scattered filesystem metadata writes cost 2.3 times their payload, but this sequential bulk write cost 1.22 times, because sequential writes fill whole chunks instead of touching the edges of many. Bulk data is cheaper per byte than small scattered edits, which is the opposite of the intuition the earlier scattered-write measurement encouraged.

A full disk

Filling the same 256 MB disk to 94 percent with distinct data completes the curve:

occupancydistinct blobsdedupsnapshot
3.3 percent7146x1.75 MB
6.3 percent3926x9.75 MB
94 percent9411.09x235 MB

Deduplication is exactly the reciprocal of occupancy. At 94 percent full there were 84 zero chunks out of 1,024, which is 8.2 percent, and one divided by 0.918 is 1.089 against a measured 1.09. Every duplicate chunk was free space. Content deduplication is not weak, it is absent, and the earlier ratios were a precise measurement of emptiness. Snapshot cost is content multiplied by 1.07, the surplus being chunk alignment.

Compaction gets faster as the machine fills. Reading and hashing all 1,024 chunks took 1.1 seconds at 94 percent occupancy against 9.8 seconds when the disk was nearly empty, because written chunks are already in the local block cache while unwritten ones must be fetched from the streamed base. The read cost of compaction falls as the machine gets fuller, which is the opposite of the upload cost.

And here a rate limit finally binds. Compacting this machine means uploading 941 blobs plus a manifest, tree, commit and ref: 945 content-generating requests. At the enforced ceiling of 180 writes per minute that is 5.3 minutes, against 2.8 minutes of pure bandwidth, so the operation is rate-limit bound rather than bandwidth bound. Projected to 1 GB it is roughly 20 minutes. This is the only workload measured here where the limit matters, and it contradicts the claim elsewhere in this note that the forge is storage limited rather than rate limited. That claim holds for ordinary syncing and fails for compaction of a populated machine.

That also promotes the portability result from a curiosity to something structural. The same compaction is a single batch commit on Forgejo or GitLab, where GitHub needs 945 separate requests. For machines of realistic size, GitHub's per-object API is not merely more expensive, it is the difference between an operation that takes seconds and one that takes tens of minutes.
