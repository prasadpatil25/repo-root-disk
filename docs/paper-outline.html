Framing

One contribution, stated three ways

The paper has a mechanism half and a measurement half, and the measurement half is the one nobody else has. Lead with the mechanism because it motivates the measurement, but the finding a reviewer will remember is that a code forge's documented limits are not its enforced limits.

Working abstract, one sentence: browser-native virtual machines all treat remote storage as read only, so machine state is trapped in one browser profile; we close the loop by committing the guest's dirty block set into an ordinary git host, and in doing so characterise what a code forge looks like when used as a storage tier.

Three claimed contributions, in the order a reviewer should meet them. First, the write-back device: an unmodified emulator, a single interception point, and a protocol that turns a machine's state into a commit. Second, the characterisation: latency, concurrency, bandwidth and rate limits of a forge under a block-storage workload, including a documented-versus-enforced discrepancy. Third, the consequence: for this workload the forge is not rate limited, it is storage limited, which relocates the hard problem from budgeting to compaction.

Holes

Unsupported claims

Each of these currently appears in the design note as an assertion. None has data. Writing them as findings would be dishonest, and a reviewer would catch at least the first three.

U7 is the one I would fix first in code rather than in an experiment. Replaying onto zeros is correct only because the base is blank. The implementation must replay onto the base, and the current prototypes would silently produce a corrupt disk the moment the base has content. It is a two-line change and a latent bug.

Experiments

Four experiments, in the order I would run them

E1. Dedup across commits

done · closed U2

Result: incremental syncs upload 2 chunks against the first sync's 5, while every commit's tree still references all 6 objects, so restore cost is constant in sync count. Content dedup was zero: the saving is incremental sync, not deduplication. Each 17 byte append cost 512 KB of new git objects.

6 syncs measured. Open follow-up: which two chunk indices are dirtied by an append, and whether 64 KB chunks cut the 512 KB per-edit cost proportionally

E2. Realistic scale

done · closed U1

Result: measured at 3, 6 and 94 percent occupancy on a 256 MB streamed disk. Deduplication turns out to be exactly the reciprocal of occupancy, so content dedup is zero and the early ratios were measuring emptiness. Snapshot cost is content times 1.07. Compaction reads get faster as the disk fills, and compaction of a full machine becomes rate-limit bound at 945 requests, the only place in the project where a limit binds.

follow-up if wanted: 1 GB rather than 256 MB, to confirm the 20 minute compaction projection and find the tab memory ceiling

E3. Compaction and re-baselining

measured · push pending

Measured: a full snapshot of the 256 MB machine is 7 distinct blobs and 1.75 MB, because 990 of 1,024 chunks are zero. Reading the disk to compute that took 9.8 s, so the operation is read bound. A re-baseline costs about the same as three or four incremental syncs, which means it can run routinely rather than as an emergency rebuild. Implemented as an orphan commit plus a forced ref update. Pending: actually pushing one, and confirming what the host reclaims, which depends on GitHub GC timing rather than on us.

remaining: push a real orphan commit, restore from it, and observe whether the repo size the API reports actually falls

E4. Replication on a second host

mapped · push pending

Finding: the API does not map, and that is the interesting part. Forgejo and GitLab expose git blobs, trees and commits read only; both instead offer a batch commit endpoint taking a file list, so a sync costing 11 requests on GitHub costs 1 on either. The portable abstraction is commit(files), not five operations, and GitHub turns out to be the most expensive host for this workload. Pending: actually pushing to one, and establishing whether the compare-and-swap in P7 has any equivalent there.

remaining: push a real commit to Forgejo or GitLab, measure the envelope, and test whether concurrent writers can be made safe without fast-forward-only refs

Not on the list, deliberately. Networking, a polished interface, multi-user support, and anything else that makes this feel like a product. None of it strengthens a claim, all of it adds surface to explain, and a short paper's prototype should be the smallest thing that supports the argument.
